# Архитектура

Этот документ отделяет факты, видимые в текущей прошивке, от деталей системы, которые ещё нужно подтвердить. Основной цикл и большинство обработчиков находятся в `src/main.cpp`.

## Компоненты

| Компонент | Назначение по коду | Реализация |
|---|---|---|
| Карта регистров | Общая RAM-карта `std::map<uint16_t,uint16_t>` с адресами 0–145 | `src/registers.cpp` |
| Modbus RTU | ESP32 — Slave с ID 16; ведущий контроллер читает карту Holding-регистров и обрабатывает команды из регистра 100; доступ к карте синхронизируется мьютексом | `src/main.cpp` |
| Wi-Fi | Режим AP+STA; собственная AP запускается всегда, STA подключается при сохранённой сети | `src/main.cpp` |
| Web | HTTP-панель, JSON API и формы настройки | `src/main.cpp`, `src/web_pages.cpp` |
| MQTT | Публикация JSON-карты и состояний, подписка на `<topic>/set`, целые команды R100/R101 | `src/main.cpp` |
| Telegram | Прежние сообщения о тревогах и отдельное уведомление о влажности R6 | `src/telegram.cpp` |
| Хранение настроек | NVS через `Preferences` для AP, Wi-Fi, MQTT, Telegram и уведомления о влажности | `src/main.cpp` |
| OTA | Обновление прошивки через веб-интерфейс без администраторского входа | `src/main.cpp` |

## Участники системы

| Участник | Взаимодействие с ESP32 | Статус сведений |
|---|---|---|
| Самодельный контроллер | Modbus Master: инициирует обмен и исполняет команды из R100 | Марка и модель не известны |
| Владелец курятника | Контроль и управление через веб-интерфейс ESP32 | Подтверждено владельцем проекта |
| SCADA-системы | Интеграция через MQTT и HTTP API | Подтверждено владельцем проекта; конкретные системы не указаны |

По сведениям владельца, на данный момент клиентов MQTT и Home Assistant нет; возможности интеграции предусмотрены на будущее.

## Критичное эксплуатационное требование

Возможность владельца подключиться к веб-интерфейсу ESP32 критична для системы. Поэтому изменения Wi-Fi, постоянной точки доступа, DNS captive portal, веб-маршрутов, авторизации и сессий требуют проверки доступа к панели как через предусмотренный сценарий подключения, так и после перезапуска устройства.

## Работа веб-интерфейса

Для уменьшения задержки навигации `ResponsiveWebServer` освобождает соединение, ожидающее первые байты HTTP не менее 1,5 с, только если в очереди уже есть другой клиент. При наличии данных или отсутствии очереди работает стандартная обработка библиотеки; начало обработки запроса и загрузка OTA не прерываются этим условием. Очень медленному клиенту может понадобиться повторный запрос. Решение использует защищённые поля текущей версии Arduino ESP32 WebServer: при обновлении платформы необходима повторная проверка, как и стендовая проверка доступа через AP и роутер, captive portal и OTA.

Логотип, стили и скрипт таблицы хранятся в прошивке. ESP32 автоматически вычисляет SHA-256 фактического содержимого каждого ресурса и добавляет полный хеш в его адрес; после изменения ресурса адрес меняется без ручного обновления номера версии. Сервер разрешает кэширование ресурса на сутки только при совпадении версии с текущим содержимым. Запрос со старой версией получает HTTP 410 и `no-store`; запрос без версии обслуживается без кэширования. Если хеш ресурса вычислить не удалось, версионированный запрос получает HTTP 503, а запрос без версии обслуживается без кэширования. HTML и динамические ответы на соответствующих маршрутах отправляются с `Cache-Control: no-store`; формат JSON и MQTT не изменён.

В каждую страницу встраивается SHA-256 ELF запущенной прошивки. `/api/status` возвращает тот же идентификатор в заголовке `X-UI-Build` без изменения JSON. При обнаружении другого идентификатора открытая страница блокирует взаимодействие и предлагает перезагрузить её; сетевую ошибку она не принимает за обновление. Проверка выполняется при опросе статуса, возврате к вкладке и восстановлении видимости. До следующей проверки уже отправленную команду отменить нельзя. Если идентификатор недоступен, сравнение невозможно; работа должна быть проверена на устройстве. Вкладки, открытые до установки этой версии и не содержащие проверку, не могут обнаружить обновление автоматически: после первой установки их следует закрыть или обновить вручную. После последующих OTA также рекомендуется обновить страницу и проверить доступ к панели; несохранённые данные форм при перезагрузке пропадут.

По словам владельца, других критичных сценариев или дополнительных ограничений на изменения пока не указано.

## Потоки данных

Аварийные биты устанавливает и сбрасывает Modbus Master; задача ESP32 — получать их состояние и информировать пользователя. Это не отменяет установленные владельцем правила уведомлений, в том числе отдельный контроль предела влажности R6.

1. Ведущий Modbus-контроллер считывает и при необходимости записывает разрешённые диапазоны карты `memo`; ESP32 отвечает как Slave.
2. Веб API и входящие MQTT-команды также меняют отдельные значения карты, чтобы пользователь и внешняя SCADA могли контролировать и управлять системой.
3. Регистр 100 передаёт команды Modbus Master: старший байт `0x01`, младший — код команды. Например, `0x0102` сбрасывает аварию датчика температуры; после выполнения Master записывает `0x0000`.
4. MQTT периодически публикует снимок всей карты в JSON; запись через API/MQTT вызывает немедленную публикацию, если клиент подключён.
5. Периодическая проверка Telegram анализирует несколько битов регистров и диапазон счётчиков ошибок и уведомляет о смене общего состояния тревоги.

Код определяет технический обмен, но не является полной спецификацией прикладной логики контроллера. Соответствие каждого регистра датчику, исполнительному механизму или режиму нужно брать из подтверждённой карты регистров.

## Наблюдаемое поведение протоколов

### Modbus RTU

- Serial2: 9600 бод, 8N1, RX GPIO 16, TX GPIO 17.
- Server ID: 16 (`0x10`).
- ESP32 работает как Modbus Slave; обмен инициирует Modbus Master.
- Реализованы функции чтения Holding-регистров (03), записи одного регистра (06) и записи нескольких (16).
- Запросы ограничены существующими адресами карты; точные ограничения и коды ошибок определяются обработчиком `handleModbus` в `src/main.cpp`.
- Карта и её значения находятся в оперативной памяти и инициализируются нулями при старте.
- Регистр 100 передаёт команды Master: старший байт `01`, младший — код команды. Например, `0x0102` — сброс аварии датчика температуры, `0x0103` — код `03`. После выполнения Master сбрасывает регистр в `0x0000`.

### MQTT

- Согласованная основа интеграции MQTT и HTTP API — снимок сырых регистров в JSON-объекте с адресами в качестве ключей; клиент разбирает значения по карте. Текущий формат снимка следует сохранить.
- Статус актуальности Master и результаты команд передаются отдельно от снимка; принятие ESP32 и обнуление регистра Master — разные состояния. Интерфейсы приведены ниже.
- Сервер, порт, учётные данные и топик настраиваются в веб-интерфейсе и сохраняются через Preferences.
- Публикуется JSON-объект вида `{"<адрес>": <значение>}` в настроенный топик.
- Команды принимаются из `<топик>/set` в виде `{"address":100,"value":258,"request_id":"cmd-1"}`. `request_id` необязателен, это строка длиной до 64 байт без нулевых байтов. Запись битов запрещена. R100 принимает только `0x0101–0x010B` и `0x01FF`; R101 — значения 1–65535. Права и занятость проверяются совместно с HTTP под мьютексом.
- Команды в `<топик>/set` необходимо отправлять без retain, а ранее сохранённые команды удалить на брокере перед подключением устройства. Используемый PubSubClient не сообщает обработчику признак retain: сохранённая команда может повторно исполниться при переподключении, если регистр уже свободен. Настройку брокера и клиентов проверить на безопасном стенде.
- Результаты MQTT-команд публикуются в `<топик>/result`, например `{"address":100,"value":258,"status":"accepted","request_id":"cmd-1"}` и затем `{"address":100,"value":258,"status":"completed","request_id":"cmd-1"}`. `completed` означает, что Master обнулил регистр; `rejected` содержит поле `reason`. Результаты веб-команд в MQTT не публикуются.
- Причины отказа: `invalid_json`, `invalid_arguments`, `invalid_request_id`, `bit_write_forbidden`, `read_only`, `invalid_value`, `register_busy`, `lock_busy`. Если адрес или значение нельзя определить, поле результата равно `null`. Некорректный `request_id` не повторяется в ответе.
- `<топик>/status` содержит, например, `{"master_status":"fresh"}`. Значения: `waiting`, `fresh`, `stale`. Публикация при подключении, изменении и каждые 10 секунд. Оба новых топика используют QoS 0 без retain; доставка не гарантирована при обрыве. Требования к broker/TLS не определены.

### Web и доступ

- Основные страницы и API зарегистрированы в `setup()` файла `src/main.cpp`.
- AP использует DNS-перехват и перенаправляет HTTP-запросы проверки сети на свой IP; неизвестные HTTP-пути через AP также перенаправляются на панель. Через роутер неизвестные пути возвращают 404. Автоматическое появление окна зависит от устройства и требует проверки на реальных телефонах; прямой HTTP-доступ по IP AP сохраняется.
- Встроенный mDNS публикует имя `chickenhouse.local` и HTTP-сервис. Имя может использоваться в локальной сети роутера при поддержке mDNS; при сбое или конфликте имён остаётся доступ по IP. Запуск mDNS и ошибки выводятся в последовательный порт. Сценарии запуска без роутера и повторного подключения требуют стендовой проверки.
- Главная страница показывает общую информацию в блоках; боковое меню ведёт к подробным страницам света, тревог, вентиляции, кормления, лаза и климата. Старый адрес `/autoChickenHous` сохранён и отвечает перенаправлением HTTP 302 на главную страницу.
- Режим администратора и пароль веб-панели удалены по запросу владельца. Любой клиент с сетевым доступом к панели может менять настройки, загружать OTA и отправлять допустимые команды без входа.
- В настройках можно сменить пароль AP (8–63 печатных ASCII-символа) без пароля администратора. Имя AP сохраняется; после смены пароля AP выполняется перезапуск и требуется переподключение.
- Кнопка GPIO27 запускает сброс пользовательских настроек после удержания не менее 3 секунд; см. `docs/hardware.md`. Физические сценарии требуют стендовой проверки.
- `POST /api/write_reg` принимает десятичные `addr` и `value` без администраторской сессии и возвращает текст `accepted` (HTTP 200), `invalid_arguments`/`invalid_value` (400), `read_only` (403), `register_busy` (409) или `lock_busy` (503). `POST /api/write_bit` отклоняется с 403 `bit_write_forbidden`.
- `GET /api/commands` возвращает состояния последних команд в виде `{"100":{"value":258,"status":"pending","unconfirmed":false},"101":{"value":0,"status":"idle","unconfirmed":false}}`. Состояния: `idle`, `pending`, `completed`, `unknown` (Master изменил ожидающую команду). Для `0x01FF` поле `unconfirmed` становится истинным через 10 секунд ожидания; это не освобождает регистр. Последние состояния хранятся только в RAM.
- `GET /api/status` дополнен полем `master_status`; `/api/data` и MQTT-снимок сохраняют исходный формат. R17 отслеживается при Modbus-записи: до первого изменения — `waiting`, после 60 секунд без изменения — `stale`, после изменения — `fresh`.
- Уровень защиты сети и ожидаемая модель угроз должны быть подтверждены владельцем; это описание кода не является аудитом безопасности.

### Telegram

- Достаточно одного чата для уведомлений; пользователь указывает его Chat ID в настройках.
- Требование владельца: предусмотреть уведомления о важных событиях, включая аварии, ошибки и выход параметров за допустимые пределы. В настройках перечисляются доступные ошибки и состояния для выбора пользователем. Повторные уведомления по умолчанию выключены; пользователь может включить их и задать периодичность. Пределы параметров настраиваются на странице «Аварии и ошибки». Полный перечень событий, параметры и значения по умолчанию ещё уточняются.
- Подтверждён контролируемый параметр: верхний предел влажности в курятнике (R6) для контроля работы осушителя. Пользователь задаёт его на странице «Аварии и ошибки»; значение по умолчанию — 95%. При превышении уведомление отправляется сразу, без дополнительной задержки.
- Настройки влажности хранятся в `configAlerts`: предел 0–100%, уведомление по умолчанию включено, повторы выключены, предлагаемый интервал 30 минут (допустимо 1–10080 минут). При нормализации повторы прекращаются; при ожидании или устаревании данных уведомление не отправляется. Проверка выполняется в отдельной задаче, состояние повторно проверяется перед отправкой после установки TLS-соединения. При неуспешной доставке предпринимается повторная попытка через 10 секунд.
- Другие существующие уведомления сохраняют прежнее поведение и пока не выбираются отдельно; их итоговый перечень согласуется отдельно.
- При наличии Wi-Fi, токена и chat ID код отправляет сообщения через HTTPS к Telegram Bot API.
- Проверяются тревоги по R1:B9, R1:B10, R3:B5, R3:B9 и сумме регистров 48–52.
- События отправляются при переходе из состояния «нет активных тревог» в «есть тревога» и обратно. Это не отдельное уведомление на каждую причину.
- Точное назначение этих битов/счётчиков и желаемые тексты подтверждает владелец.

## Жизненный цикл

`setup()` загружает сохранённые настройки, создаёт защиту карты регистров, запускает Wi-Fi, DNS captive portal, веб-сервер, Modbus и MQTT; затем отправляет сообщение о запуске через Telegram, если настройки позволяют. `loop()` обслуживает DNS, HTTP и MQTT, пытается восстановить подключения и раз в 10 секунд проверяет Wi-Fi и тревоги.

## Обслуживание документации

При изменениях протокола обновляйте `docs/register-map.md` и соответствующие разделы здесь. При изменении платы, GPIO, скорости линии или электрической схемы обновляйте `docs/hardware.md`. Удаляйте пометку «не подтверждено» только после сверки с владельцем/первичной спецификацией.
